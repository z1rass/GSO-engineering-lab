# Domain docs

Use a single domain context.

Before exploring or changing behavior, read the root CONTEXT.md
and relevant decisions in docs/adr/.

For product scope, read docs/mvp-product-spec.md.
Consult docs/design-interview.md when decision history is needed.
Implementation specifications and ticket drafts remain proposals
where their status says so.

Use the glossary's terms. Surface conflicts with accepted decisions
instead of silently replacing them.

If a referenced domain document is absent, continue; create domain
documents when terminology or decisions are actually resolved.
